## Downgrade experiment (RPM wipe + snapshot restore)

**Binary downgrade of Elasticsearch data directories is not supported.** After 8.19 → 8.18 package reinstall you must wipe `path.data` and restore from a snapshot taken on 8.18 (or an earlier compatible snap).

```text
scripts/downgrade-es-node-8184.sh   # per-node RPM path (preserve certs + keystore)
python complete_downgrade_restore.py
python finish_downgrade_restore_es04.py
```

Critical restore notes:

1. Preserve `/etc/elasticsearch/certs` and `elasticsearch.keystore` across RPM reinstall.
2. Re-apply production `elasticsearch.yml` (package defaults overwrite lab paths/roles).
3. Snapshot restore: use **explicit** `feature_states` (e.g. `security`, `kibana`, `fleet`, `async_search`) — `["*"]` is rejected.
4. After wipe, elastic password is new until security feature state restore; then the snapshot password applies. Store under `secrets/elastic-password` (gitignored).
5. Without a **data_hot** node, indices with hot tier preference stay unassigned.

### es04 rejoin after downgrade

| Scenario | Result |
|----------|--------|
| es01–es03 **RPM wipe + new cluster UUID** + restore, es04 still 8.19 with old cluster metadata | **es04 does not rejoin** (cluster UUID / version mismatch) |
| es01–es03 **Hyper-V restore** to `pre-upgrade-system-8.18.4-with-apm` (same cluster UUID as es04) | **es04 rejoins** on mixed-version rolling-upgrade path |
| All nodes version-aligned | Normal green when tiers and replica counts match capacity |

Add `data_hot` on at least one 8.18 node (lab: es03) before expecting hot-tier replicas:

```powershell

# or after HV restore of es01–es03:
python restore_es01_03_hot_es04_rejoin.py
```

## Yellow health in mixed version (fix + limits)

```powershell
python fix_yellow_mixed_version.py
```

This sets `number_of_replicas: 0` **and** `auto_expand_replicas: false` on non-restricted indices.  
`auto_expand_replicas: "0-1"` alone will put replicas back to 1 and leave the cluster yellow.

**Residual yellow** after the fix is normal when:

- Primaries of system indices (`.security-7`, `.security-profile-8`) or reserved streams (`.fleet-actions-results`) live on the **newer** node (8.19.x).
- Older nodes cannot take those replicas (`node_version` decider).
- Elastic **forbids** overriding replica settings on those system indices.

All **primaries** assigned + high `active_shards_percent` ≈ safe for lab use. True **green** requires version alignment (upgrade remaining 8.18 nodes to 8.19.x, or restore every ES node to the same Hyper-V snap).
